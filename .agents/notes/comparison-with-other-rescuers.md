# 依据：与生态里其他"回合救援"做法的对照（2026-10-26）

状态：生效

## 背景

维护者给出四条外部资料（`harn_vm` 的 AUTO-CONTINUE、GitLab 的 `MarkupLeakGuard`、npm 上的
`@jayyuen66/dsh-session-rescue`），要求判断哪些能在本仓落地。资料本身不保证正确，逐条对照了实现。

## 结论

| 资料里的做法 | 判断 | 落地 |
|---|---|---|
| ① 显式确认 stop_reason 不是长度截断 | **真问题，采纳** | 见下 |
| ② U+FF5C 全角竖线、U+2581 折叠 | **一半已覆盖、一半不需要** | 见下 |
| ③ 用 `todo/write` 快照里未完成项当信号 | **有价值但不是本插件** | 不落地 |
| ④ 监听 `agent/request-error`，限流返回 `retry` | **已有实现覆盖** | 不落地 |

## ① 长度截断：比原先判断的更严重

原先 `docs/ARCHITECTURE.md` 写的是"无法区分，靠上限兜底"。核过宿主源码后确认更糟：**`turn-stopping`
对 `max-tokens` 的回合照常派发**（`agent-loop/src/agent.ts:361`），所以一个"思考被截断且尾部带泄漏标记"
的回合会被当成空转续跑——等于再买一份预算给它继续被截断。

修法：不用启发式猜 stop_reason，改用两侧都已发布的账：**收尾消息的 `usage.outputTokens` 与
会话上一次请求的 `config.maxTokens` 相等**即视为被截断。宿主自己的 `max-tokens` 判定晚一个事件
（在 `turn/end`），那时消息已经排队，来不及撤。

失败朝向是刻意的：读不到 ceiling 或读不到 usage 时判"未耗尽"。判错的 `true` 会让插件在最该救时沉默，
判错的 `false` 只花掉连击预算里的一次。

## ② 全角竖线与 U+2581

- **U+FF5C 已被覆盖**：`protocol.ts` 在匹配前做 NFKC，全角竖线折成 ASCII `|`。资料提的坑在本仓不成立。
- **U+2581 不需要处理**：实测 `</｜｜DSML｜｜tool▁calls>` 归一后仍命中，因为判据锚定的是**标记本身**
  （`||DSML||`），不是后面的 token 名。tokenizer 把空格写成 `▁` 只影响 token 名，落不进匹配窗口。
  已加一条测试把这件事钉住，免得日后有人"顺手"把判据改成匹配完整 token 反而弄坏。

## ③ todo 快照信号：不落地

那是"是不是干完了"的信号，适合"通用补跑"；本插件的判据是"是不是被协议层打断"，两者目标不同。
把 todo 信号并进来会让误伤面从"确证的空转"扩大到"有未完成项的一切回合"。留作未来的独立 PR。

## ④ 限流重试：不落地

宿主已装 `@deepseek-ai/dsh-llm-retry`，默认重试码就含 `RATE_LIMIT`，走的正是 `agent/request-error`
瀑布。再写一份是同一条策略的两个执行体，会打架。

## 影响

- ① 让"续跑"与"截断"分家；若上游换成真正可读 stop_reason 的接缝，这段会计判断可以删掉。
- ② 的测试是**反向控制**：它保护的是"判据锚在标记上"这个设计，而不是某个字符串。
- ③④ 若将来做"通用回合救援套件"，这份对照是起点。
